# פרומפטים ללאבאבל — לפי הסדר

הוראות שימוש:
- העתק כל פרומפט **בשלמותו** לצ'אט של לאבאבל, אחד בכל פעם, ובסדר הזה.
- אחרי כל שלב: בדוק בפריוויו שהוא עובד לפני שעוברים לשלב הבא. אם משהו שבור —
  תאר ללאבאבל את מה שראית, אל תעבור הלאה.
- בשלב 0 לאבאבל יבקש לחבר Supabase. אשר. בשלב 3 הוא יבקש להפעיל Lovable AI.
  אשר.
- אחרי שלב 7: חבר את הפרויקט ל-GitHub (`shybarm/HaBodeket`) דרך
  GitHub → Connect בלאבאבל, ואז ממשיכים לחדד מתוך הקוד.
- המסמך `docs/SPEC.md` הוא מקור האמת. אם לאבאבל מחליט אחרת ממנו — תקן אותו.

## שלב 0 — בסיס, סכמה, התחברות ותפקידים

```
בנה אפליקציית ווב בעברית בשם "הבודקת" לניהול ואימות שאלות טריוויה לשעשועון
טלוויזיה. React + TypeScript + Tailwind + shadcn/ui + Supabase.

כל הממשק בעברית ובכיוון RTL: הגדר dir="rtl" ו-lang="he" על אלמנט ה-root, וודא
שכל קומפוננטות shadcn נראות נכון ב-RTL. אין אף מחרוזת באנגלית בממשק, כולל
הודעות שגיאה ומצבי ריק.

חבר Supabase וצור את הסכמה הבאה:

1. enum app_role עם הערכים: 'admin', 'checker', 'writer'.
2. טבלת profiles: id uuid PK שמצביע ל-auth.users עם ON DELETE CASCADE,
   full_name text not null, email text, created_at.
3. טבלת user_roles נפרדת: id, user_id → profiles, role app_role,
   unique(user_id, role). חשוב מאוד: אל תשים עמודת role על profiles. התפקידים
   תמיד בטבלה נפרדת.
4. פונקציית has_role(_user_id uuid, _role app_role) returns boolean, מסוג
   SECURITY DEFINER עם search_path ריק, שבודקת קיום שורה ב-user_roles. כל
   מדיניות RLS שתלויה בתפקיד חייבת לקרוא לפונקציה הזאת ולא לקרוא תפקיד מתוך
   ה-JWT.
5. טריגר on auth user created שיוצר profile. המשתמש הראשון שנרשם במערכת מקבל
   אוטומטית את התפקיד 'admin'; כל השאר נרשמים בלי תפקיד וממתינים שמנהל ישבץ
   להם תפקיד.
6. טבלת writers: id, display_name text unique not null, user_id → profiles
   nullable, active boolean default true. זו טבלת הכותבים כפי שהם מופיעים בגוגל
   שיט, עם מיפוי אופציונלי למשתמש אמיתי.
7. enum question_status עם הערכים בדיוק: 'draft', 'writer_reviewed',
   'verifying', 'verified', 'needs_rewrite', 'insufficient_sources',
   'rejected', 'checker_approved', 'assigned', 'used'.
8. טבלת questions: id, writer_id → writers not null, category text not null,
   text text not null, option_count int check in (2,3,4), correct_index int
   not null (אינדקס 1-based), round_number int nullable check between 1 and 7,
   difficulty int nullable check between 1 and 5, writer_notes text,
   status question_status default 'draft', rejection_reason text,
   suggested_text text, rewrite_decision text, dossier_summary text,
   import_batch_id uuid nullable, source_row int, created_by → profiles,
   created_at, updated_at.
   הוסף אילוצים: correct_index <= option_count, וכן אילוץ שמקשר סיבוב למספר
   תשובות — סיבובים 1 עד 3 מחייבים 4 תשובות, סיבובים 4 עד 6 מחייבים 3 תשובות,
   סיבוב 7 מחייב 2 תשובות (round_number יכול להיות null).
9. טבלת question_options: id, question_id → questions ON DELETE CASCADE,
   position int (1-based), text not null, is_correct boolean default false,
   one_liner text, unique(question_id, position).
10. טבלת import_batches: id, source text, source_ref text, imported_by →
    profiles, row_count int, created_at.
11. טבלת audit_log: id, actor_id → profiles, entity text, entity_id uuid,
    action text, before jsonb, after jsonb, created_at.

הפעל RLS על כל הטבלאות. כרגע: מנהל רואה ועושה הכל; בודק קורא הכל; כותב רואה
ועורך רק שאלות שה-writer_id שלהן ממופה למשתמש שלו.

בנה מסך התחברות והרשמה (אימייל וסיסמה), ושלד ניווט עם סרגל צד בעברית ובצד
ימין, עם הפריטים: לוח בקרה, מחסן השאלות, ייבוא, תור בדיקה, מתמודדים, ניהול.
פריטים מוצגים לפי תפקיד. בשלב הזה הדפים עצמם יכולים להיות ריקים, חוץ מדף
"ניהול" שבו מנהל רואה את כל המשתמשים ויכול לשבץ ולהסיר תפקידים.
```

## שלב 1 — ייבוא מגוגל שיט

```
בנה את דף הייבוא. השיט של הלקוח בנוי בעמודות האלה, בעברית, ובסדר הזה:

כותב השאלה | קטגוריה | שאלה | תשובה 1 | תשובה 2 | תשובה 3 | תשובה 4 | תשובה נכונה | הערות

חשוב מאוד: העמודה "תשובה נכונה" מכילה מספר, אינדקס 1-based של התשובה הנכונה
(למשל 3 פירושו "תשובה 3"). היא לא מכילה את טקסט התשובה.

דוגמת שורות אמיתיות מהשיט:
גרנות | תחבורה | איפה אין תחנת רכבת? | אשקלון | כוכב יאיר | אור יהודה | בית שאן | 3 |
גרנות | חי וצומח | מי מהבאים הוא דג? | נמנמן | ישנן | חורפן | חולמן | 2 |

שתי דרכי ייבוא:
1. העלאת קובץ CSV או הדבקת תוכן CSV. זו הדרך העיקרית. נתח CSV עם תמיכה
   בעברית וב-UTF-8 BOM, ועם שדות במרכאות שמכילים פסיקים.
2. הדבקת קישור לגוגל שיט. חלץ את מזהה הגיליון מה-URL והבא
   https://docs.google.com/spreadsheets/d/<id>/export?format=csv. אם הבקשה
   נכשלת כי הגיליון לא ציבורי, הצג שגיאה מנומקת בעברית שמסבירה שצריך לפרסם
   את הגיליון או להוריד אותו כ-CSV ולהעלות בדרך הראשונה. אל תיכשל בשקט.

זיהוי עמודות לפי שמות הכותרות בעברית, לא לפי מקום. התעלם מעמודות עודפות או
נגררות בשיט. התעלם משורות ריקות לגמרי.

מספר התשובות של כל שאלה נגזר ממספר עמודות התשובה הלא-ריקות: 4, 3 או 2.

לפני הייבוא הצג תצוגה מקדימה כטבלה, שורה-שורה, עם סטטוס לכל שורה: תקין, אזהרה
או שגיאה, והסבר בעברית. חסום ייבוא של שורה אם:
- "תשובה נכונה" ריקה, אינה מספר, או גדולה ממספר התשובות שיש בשורה.
- השאלה ריקה, או שתשובה 1 או תשובה 2 ריקות.
- יש "חור" ברצף התשובות, למשל תשובה 3 ריקה אבל תשובה 4 מלאה.
אם שאלה עם אותו נוסח (אחרי נרמול רווחים) כבר קיימת במערכת — הצג אזהרה ודלג
עליה, אל תיצור כפילות.

הייבוא כולו טרנזקציה אחת שיוצרת import_batch אחד. שם כותב שלא קיים בטבלת
writers נוצר אוטומטית. כל השאלות נכנסות במצב 'draft'. סמן על כל שאלה את
source_row כדי שאפשר יהיה לאתר אותה חזרה בשיט. אפשר למנהל לבטל batch שלם כל
עוד אף שאלה בו לא שובצה למתמודד.
```

## שלב 2 — מחסן השאלות וכרטיס שאלה

```
בנה את מחסן השאלות ואת כרטיס השאלה.

מחסן השאלות: טבלה עם עמודות נוסח השאלה (מקוצר), קטגוריה, כותב, מספר תשובות,
סיבוב, קושי ומצב. סינון לפי מצב, כותב, קטגוריה, סיבוב וקושי; חיפוש טקסט חופשי
בנוסח השאלה ובתשובות; מיון; עימוד. בחירה מרובה עם פעולות אצווה: "שלח לבדיקה
אוטומטית" ו"שייך לכותב אחר".

תצוגת המצבים בתגי צבע ובעברית:
ממתין לבדיקה = אפור, נבדק ע"י הכותב = אפור כהה, בבדיקה = כחול,
אושר אוטומטית = ירוק, דורש ניסוח מחדש = כתום, חסרים מקורות = צהוב,
נפסל = אדום, אושר ע"י בודק = ירוק כהה, שובץ = סגול, נשאל = אפור בהיר.

תוויות קושי: 1 קל, 2 בינוני-קל, 3 בינוני, 4 קשה, 5 קשה מאוד.

כרטיס שאלה הוא מסך העבודה המרכזי. הוא מציג:
- נוסח השאלה, הקטגוריה, הכותב, הסיבוב והקושי. הקושי נבחר מ-1 עד 5.
- רשימת התשובות לפי הסדר, כשהתשובה הנכונה מסומנת בבירור.
- אזור "תיק התשובה" — כרגע ריק, נבנה בשלב הבא.
- טיימליין של כל מה שקרה לשאלה, שנקרא מטבלת audit_log.
- כפתור "בדיקה ראשונה — עברתי על השאלה" שמעביר ממצב 'draft' ל-'writer_reviewed'.
  זמין לכותב של השאלה ולמנהל.
- אפשרות עריכה של הנוסח והתשובות, זמינה רק במצבים 'draft', 'needs_rewrite',
  'insufficient_sources' ו-'rejected'. עריכת נוסח של שאלה שכבר אושרה מחזירה
  אותה ל-'draft' ומבטלת את האישור, עם אישור מהמשתמש לפני כן; עריכה אסורה
  לחלוטין במצבים 'assigned' ו-'used'.
- שינוי שיוך לכותב אחר.

כל שינוי מצב, עריכה ושיוך נכתבים ל-audit_log עם המשתמש שביצע, הערך לפני
והערך אחרי.
```

## שלב 3 — מנוע האימות האוטומטי

```
בנה את מנוע האימות. זה הלב של המערכת, אז דייק בדיוק לפי מה שכתוב כאן.

צור את הטבלאות:
- enum verdict עם הערכים: 'approved', 'rejected', 'needs_rewrite',
  'insufficient_sources'.
- טבלת verifications: id, question_id → questions ON DELETE CASCADE, verdict,
  confidence numeric(3,2), model text, writer_choice_correct boolean,
  found_correct_index int, multiple_correct boolean default false,
  reasoning text, clarity_issues jsonb default '[]', suggested_text text,
  difficulty_suggestion int, raw_response jsonb, question_snapshot jsonb,
  created_at. בדיקה חוזרת יוצרת שורה חדשה ולא דורסת קודמת.
- טבלת verification_sources: id, verification_id → verifications ON DELETE
  CASCADE, url text, domain text, publisher text, title text, tier text,
  quote text, supports_index int, checked_ok boolean default true.
- הוסף ל-questions עמודת latest_verification_id → verifications nullable.

צור Edge Function בשם verify-question שמקבלת question_id, ומריצה אימות דרך
Lovable AI עם מודל שיש לו חיפוש ווב. השתמש ב-google/gemini-2.5-pro.

ה-system prompt של המודל, מילה במילה:
---
אתה בודק עובדות עבור שעשועון טריוויה בטלוויזיה. מטרתך היחידה: לקבוע אם התשובה
שהכותב סימן כנכונה היא אכן נכונה וחד-משמעית, ולגבות זאת בשני מקורות מוסמכים
ובלתי תלויים.

כללי מקורות — מחייבים:
- אסור בהחלט להסתמך על ויקיפדיה בכל שפה, על כל ויקי פתוח כמו fandom, על
  בלוגים, פורומים, רשתות חברתיות, אתרי טריוויה או מצרפי תוכן.
- מותר: אתרי ממשלה ורשויות, הגוף הרשמי שהנושא עצמו (למשל רכבת ישראל לשאלה על
  רכבות), הלמ"ס וגופי סטטיסטיקה, מקורות אקדמיים, אנציקלופדיות ממוסדות בעריכה
  מקצועית, ארגונים בינלאומיים, כלי תקשורת מרכזיים, מוזיאונים וארכיונים
  לאומיים.
- שני המקורות חייבים להיות מדומיינים שונים ובלתי תלויים זה בזה.
- החזר רק כתובות URL שראית בתוצאות החיפוש וקראת. אל תמציא כתובות ואל תנחש
  כתובת סבירה. אם אין לך שני מקורות קבילים — החזר verdict בערך
  "insufficient_sources".

כללי הכרעה:
- אם התשובה שהכותב בחר שגויה, החזר verdict "rejected", ובשדה
  rejection_reason_he כתוב בדיוק מה נמצא ומהי התשובה הנכונה.
- אם התשובה שהכותב בחר נכונה אך גם תשובה אחרת נכונה, סמן multiple_correct
  בערך true והחזר verdict "needs_rewrite". בשעשועון אסור שיהיו שתי תשובות
  נכונות, ולכן זהו מצב פסילה.
- אם השאלה עמומה, לא מעוגנת בזמן, סובייקטיבית, או שהתשובות אינן זרות הדדית,
  החזר verdict "needs_rewrite", ובשדה suggested_question_text_he הצע ניסוח
  מדויק שפותר את הבעיה בלי לשנות את כוונת הכותב ובלי לשנות את התשובות.
- אם התשובה נכונה אך לא מדויקת, למשל נכונה רק בקירוב או נכונה לתאריך אחר,
  החזר "rejected" עם הסבר מדויק.
- רק אם התשובה נכונה, יחידה, והשאלה ברורה — החזר "approved".
- אם אינך בטוח, אל תאשר. confidence נמוך מ-0.75 אינו מצדיק approved.

תיק התשובה:
- correct_blurb_he: בין שניים לארבעה משפטים בעברית על התשובה הנכונה — מה היא,
  עובדה אחת מעניינת שניתן להקריא בשידור, ועיגון של מקום, תאריך או גוף.
- לכל תשובה לא נכונה: שורה אחת קצרה שמסבירה מה היא כן, בסגנון
  "ירושלים — בירת ישראל".

כל הטקסט המיועד לקריאה — reasoning_he, rejection_reason_he, clarity_issues_he,
suggested_question_text_he והבלורבים — בעברית, גם אם המקורות באנגלית.
החזר JSON בלבד לפי הסכמה שניתנה, בלי שום טקסט מסביב.
---

ה-user prompt מורכב מנוסח השאלה, הקטגוריה, שם הכותב, רשימת התשובות ממוספרת,
מספר התשובה שהכותב סימן כנכונה יחד עם הטקסט שלה, הערות הכותב, ותאריך הבדיקה
של היום.

המודל חייב להחזיר JSON במבנה הזה בדיוק:
{
  "verdict": "approved | rejected | needs_rewrite | insufficient_sources",
  "confidence": 0.0,
  "writer_choice_correct": true,
  "found_correct_index": 1,
  "multiple_correct": false,
  "multiple_correct_indexes": [],
  "reasoning_he": "",
  "rejection_reason_he": null,
  "clarity_issues_he": [],
  "suggested_question_text_he": null,
  "dossier": {
    "correct_blurb_he": "",
    "distractors": [{ "index": 1, "one_liner_he": "" }]
  },
  "sources": [{ "url": "", "publisher": "", "title": "", "tier": "",
                "quote": "", "supports_index": 1 }],
  "difficulty_suggestion": 3
}

אחרי שהמודל חוזר, ה-Edge Function מבצעת אימות משלה בצד השרת ולא סומכת על
המודל:
1. ולידציה של ה-JSON מול הסכמה.
2. לכל מקור: נרמול ה-URL וחילוץ הדומיין הרשום.
3. פסילת דומיין מול רשימת חסימה: כל wikipedia.org בכל שפה, wikidata,
   wikiquote, wikivoyage, dbpedia, fandom.com, wikia, כל דומיין שמסתיים
   ב-.wiki, medium.com, substack.com, blogspot, wordpress.com, reddit.com,
   quora.com, stackexchange, stackoverflow, facebook.com, instagram.com,
   x.com, twitter.com, tiktok.com, pinterest, scribd.com, coursehero,
   slideshare, ואתרי טריוויה וחידונים. מקור שנפסל מסומן ב-checked_ok=false
   ואינו נספר.
4. בקשת HTTP לכל URL שנותר. סטטוס שאינו 2xx — המקור אינו נספר. זה מה שמונע
   לינקים מומצאים.
5. דרישת אי-תלות: לפחות שני מקורות שעברו, עם דומיינים רשומים שונים.
6. אם נותרו פחות משני מקורות קבילים, או ש-confidence קטן מ-0.75, הכרעת
   המערכת היא 'insufficient_sources', גם אם המודל החזיר approved. הכרעת השרת
   דורסת את המודל.

לאחר מכן המערכת שומרת את ה-verification ואת המקורות, כותבת את one_liner לכל
תשובה לא נכונה בטבלת question_options, את ה-blurb ל-dossier_summary, ומעדכנת
את מצב השאלה לפי ההכרעה: approved → 'verified', rejected → 'rejected' עם
rejection_reason, needs_rewrite → 'needs_rewrite' עם suggested_text,
insufficient_sources → 'insufficient_sources'. הכל נרשם ב-audit_log.

בזמן הריצה מצב השאלה הוא 'verifying' כדי שלא תורץ בדיקה כפולה במקביל. אם
הקריאה למודל נכשלה, החזר את השאלה למצב הקודם והצג שגיאה בעברית.

בכרטיס השאלה הוסף כפתור "הרץ בדיקה אוטומטית", זמין לכותב של השאלה, לבודק
ולמנהל. במחסן השאלות אפשר להריץ בדיקה על בחירה מרובה, אבל בתור, בקצב של עד
שלוש שאלות במקביל.
```

## שלב 4 — תיק התשובה ומסלול השכתוב

```
בנה את תצוגת "תיק התשובה" בכרטיס השאלה, ואת מסלול הטיפול בשאלה שלא עברה.

תיק התשובה, בעיצוב נקי שאפשר להקריא ממנו בשידור:
- כותרת "התשובה אושרה" או "השאלה נפסלה", עם תאריך הבדיקה ואחוז הביטחון.
- הבלורב על התשובה הנכונה.
- רשימת התשובות הלא נכונות, כל אחת עם השורה שלה. למשל:
  ירושלים — בירת ישראל
  אתונה — בירת יוון
- רשימת המקורות: כל מקור כקישור שנפתח בחלון חדש, עם שם הגוף, סוג המקור
  בעברית (ממשלתי, גוף רשמי, אקדמי, אנציקלופדיה, תקשורת, ארגון בינלאומי,
  סטטיסטיקה, מוזיאון וארכיון), והציטוט שמוכיח את התשובה.
- ההנמקה של הבודק האוטומטי.
- היסטוריית הבדיקות: אם רצו כמה בדיקות, הצג את האחרונה ואפשר לפתוח קודמות.

אם השאלה במצב 'rejected': תיבה אדומה בראש הכרטיס עם הכותרת "השאלה נפסלה",
הסיבה המלאה, ומה המערכת מצאה כתשובה הנכונה. כפתור "תקן ושלח לבדיקה חוזרת"
שפותח עריכה.

אם השאלה במצב 'needs_rewrite': תיבה כתומה עם הכותרת "השאלה דורשת ניסוח מחדש",
רשימת הבעיות שהמערכת מצאה בניסוח, והשוואה זה לצד זה של הניסוח הקיים מול הניסוח
שהמערכת הציעה. שלושה כפתורים:
- "אשר את הניסוח המוצע" — מחליף את נוסח השאלה בניסוח המוצע, שומר
  rewrite_decision='accepted', ומעביר את השאלה ל-'writer_reviewed' כדי שתרוץ
  בדיקה חוזרת.
- "לחשיבה על ניסוח מחדש" — שומר rewrite_decision='rethink' ומעביר ל-'draft',
  בלי לשנות את הנוסח. השאלה מסומנת במחסן כממתינה לשכתוב של הכותב.
- "כתוב ניסוח משלי" — פותח עריכה חופשית של הנוסח.
אם המערכת מצאה יותר מתשובה נכונה אחת, הצג את זה בבירור: אילו תשובות נמצאו
נכונות ולמה, כי זו הסיבה הנפוצה לפסילה.

אם השאלה במצב 'insufficient_sources': תיבה צהובה — "לא נמצאו שני מקורות
מוסמכים לאימות התשובה", הסבר שוויקיפדיה אינה מקור קביל במערכת, וכפתורים
"נסה בדיקה חוזרת" ו"תקן את השאלה".

כל הפעולות האלה זמינות לכותב של השאלה ולמנהל.
```

## שלב 5 — תור הבדיקה של הבודק

```
בנה את דף "תור בדיקה", שמיועד לבעלי התפקיד בודק ומנהל.

הדף מציג את כל השאלות במצב 'verified' — כלומר אושרו אוטומטית וממתינות לאישור
אנושי — בתור עבודה נוח: רשימה בצד אחד, וכרטיס מלא בצד השני, עם כפתורי "הבא"
ו"הקודם" ועם קיצורי מקלדת.

בכרטיס הבודק רואה את השאלה, התשובות, תיק התשובה המלא כולל כל המקורות
כקישורים לחיצים, וההנמקה. הוא יכול:
- לשנות את דירוג הקושי מ-1 עד 5.
- לבחור את הסיבוב, מתוך הסיבובים שתואמים את מספר התשובות של השאלה: שאלה עם 4
  תשובות שייכת לסיבובים 1 עד 3, שאלה עם 3 תשובות לסיבובים 4 עד 6, ושאלה עם 2
  תשובות לסיבוב 7. אל תאפשר בחירה שאינה תואמת.
- ללחוץ "נבדק ואושר ע"י בודק", עם תיבת הערה אופציונלית. הפעולה מעבירה את
  השאלה ל-'checker_approved' ונרשמת בטבלת checker_approvals עם מזהה הבודק
  והתאריך.
- ללחוץ "החזר לכותב" עם נימוק חובה בעברית. הפעולה מעבירה את השאלה
  ל-'needs_rewrite' ושומרת את הנימוק, גם אם הבדיקה האוטומטית אישרה אותה. שיקול
  הבודק עליון על הבדיקה האוטומטית.

צור את טבלת checker_approvals: id, question_id → questions ON DELETE CASCADE,
checker_id → profiles, note text, created_at, unique(question_id, checker_id).
בודק אינו יכול לערוך את נוסח השאלה או את התשובות, רק לאשר, להחזיר, ולקבוע
קושי וסיבוב.
```

## שלב 6 — מתמודדים ושיבוץ

```
בנה את ניהול המתמודדים והשיבוץ. זמין למנהל ולעורך התוכנית בלבד (תפקיד admin).

טבלת contestants: id, name text not null, notes text, active boolean default
true, created_at. דף לניהולם.

טבלת assignments: id, question_id → questions ON DELETE CASCADE, contestant_id
→ contestants, round_number int, assigned_by → profiles, is_active boolean
default true, transferred_from uuid nullable שמצביע על assignments, 
transfer_reason text, created_at. צור אינדקס unique חלקי על question_id
במקום שבו is_active הוא true, כדי שלכל שאלה יהיה שיבוץ פעיל אחד בלבד.

כלל הברזל של המערכת: אחרי שיבוץ שאלה למתמודד לא ניתן לבטל את השיבוץ, אפשר רק
להעביר אותה למתמודד אחר. ולכן:
- אין בשום מקום בממשק כפתור "בטל שיבוץ" או "הסר מתמודד".
- מדיניות ה-RLS אוסרת DELETE על assignments על כל התפקידים, כולל מנהל.
- העברה מתבצעת דרך פונקציית RPC אחת בשם transfer_assignment שמקבלת את מזהה
  השיבוץ, את המתמודד החדש ונימוק חובה, ועושה הכל בטרנזקציה אחת: מסמנת את
  השיבוץ הקיים כלא פעיל, ויוצרת שיבוץ חדש עם transferred_from שמצביע על הקודם
  ועם transfer_reason. כך שרשרת ההעברות נשמרת במלואה ואפשר לראות את כל
  ההיסטוריה.

שיבוץ מותר רק לשאלה במצב 'checker_approved', ורק אם יש לה דירוג קושי וסיבוב.
אם אין — הסבר בעברית מה חסר. השיבוץ מעביר את השאלה למצב 'assigned'.

דף השיבוץ מציג את המתמודדים, וליד כל אחד את השאלות שהוקצו לו לפי סיבוב ועם
דירוג הקושי, כדי שהעורך יראה אם מתמודד קיבל שאלות קשות מדי או קלות מדי. מצד
שני, מאגר השאלות המאושרות שממתינות לשיבוץ, עם סינון לפי סיבוב, קושי וקטגוריה.

בכרטיס השאלה הוסף את פרטי השיבוץ ואת שרשרת ההעברות בטיימליין, עם הנימוק לכל
העברה. כל שיבוץ והעברה נכתבים גם ל-audit_log.

הוסף פעולה "סמן כנשאלה בשידור" שמעבירה שאלה מ-'assigned' ל-'used'.
```

## שלב 7 — לוח בקרה, ייצוא וליטוש

```
השלם את המערכת.

לוח בקרה, שזה הדף הראשי אחרי התחברות:
- כרטיסי מנייה לפי מצב: ממתינות לבדיקה, בבדיקה, אושרו אוטומטית, דורשות ניסוח
  מחדש, חסרים מקורות, נפסלו, אושרו ע"י בודק, שובצו. לחיצה על כרטיס פותחת את
  מחסן השאלות מסונן לאותו מצב.
- טבלת כיסוי סיבובים: לכל סיבוב מ-1 עד 7, כמה שאלות מאושרות ע"י בודק יש, כמה
  מהן שובצו וכמה פנויות, ופילוח לפי דירוג קושי. זה הנתון החשוב ביותר לעורך
  התוכנית.
- פילוח לפי כותב: כמה שאלות הגיש, כמה אושרו, כמה נפסלו, ואחוז האישור שלו.
- פילוח לפי קטגוריה.
- רשימת הפעילות האחרונה מתוך audit_log.
כותב רואה בלוח הבקרה רק את הנתונים שלו.

ייצוא:
- ייצוא CSV של השאלות לפי הסינון הנוכחי, בקידוד UTF-8 עם BOM כדי שהעברית
  תיפתח נכון באקסל.
- "דף עורך" להדפסה: לכל שאלה מודפסים הנוסח, התשובות עם סימון הנכונה, דירוג
  הקושי, הסיבוב, המתמודד המשובץ, ותיק התשובה המלא כולל השורה על כל תשובה לא
  נכונה והמקורות. זה הדף שהמנחה והעורך מחזיקים ביד בשידור.

ליטוש:
- ודא שכל המערכת ב-RTL תקין: טבלאות, תפריטים נפתחים, דיאלוגים, טוסטים, תאריכים
  ושדות מספר.
- אין אף מחרוזת באנגלית בממשק. עבור על כל מצבי השגיאה ומצבי הריק וודא שיש
  בהם טקסט עברי מועיל שמסביר מה לעשות.
- מצבי טעינה בכל מקום שיש קריאת רשת, ובמיוחד בבדיקה האוטומטית שלוקחת זמן.
- התאמה למסך נייד, כי הבודק עשוי לעבוד מהטלפון.
- בדוק את כל מדיניות ה-RLS: כותב לא יכול לראות או לערוך שאלות של כותב אחר,
  בודק לא יכול לערוך נוסח שאלה, ואף אחד לא יכול למחוק שיבוץ.
```
